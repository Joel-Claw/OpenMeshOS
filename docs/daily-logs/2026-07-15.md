## Development Work

### Fix: nRF52 BLE OTA Build Failure

The July 13 commit (bd5cef9) implemented nRF52 BLE OTA DFU via Adafruit BLEDfu service but introduced a build error: `_dfuService.start()` was called, but `BLEDfu` (inheriting from `BLEService`) does not have a `start()` method. The Adafruit BLEDfu class only exposes `begin()`.

**Root cause**: The BLEDfu service uses a write-authorize callback on its DFU control characteristic (UUID 0x1531). When the companion app writes 0x01 (START_DFU) to that characteristic, BLEDfu internally saves peer bond data, sets GPREGRET=0xB1, disables the SoftDevice, and jumps to the bootloader. There is no public API to trigger this from the application side.

**Fix**: Replaced the `_dfuService.start()` call with a log message explaining that the companion app should write directly to the DFU control characteristic (UUID 0x1531) via Nordic DFU protocol. The firmware update characteristic (UUID 0x0006) on our companion service serves as a notification mechanism only, so the companion app can share OTA UI code between ESP32 and nRF52.

**The correct nRF52 OTA flow:**
1. Companion app discovers both services: our companion service (0xFEDC) and the DFU service (0x1530)
2. Companion app writes 0x01 to DFU control characteristic (0x1531) to trigger DFU
3. BLEDfu callback saves peer data, sets GPREGRET, jumps to bootloader
4. Bootloader advertises as DFU target, companion app connects and transfers firmware
5. Bootloader verifies and reboots into new application
